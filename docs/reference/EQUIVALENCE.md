# Cross-format equivalence contract

Every bundle decodes into the same format-independent
[`GaussianCloudData`](GAUSSIAN_MODEL_CONTRACT.md). This document defines what
"equivalent" means when one source model is encoded into PLY, SPZ, **and** SOG,
and derives the tolerances the cross-format tests enforce.

The tests are `tests/equivalence/test_equivalence.cpp` (PLY against SPZ) and
`tests/equivalence/test_sog_equivalence.cpp` (PLY against SOG); the fixture
triples are generated by `tools/generate_equivalence_fixtures.py`.

## 1. Why this test exists

The three decoders are independent implementations that must land on the same
model. Several claims are asserted nowhere else:

- the RDF→RUB reference-frame conversion
  ([ADR 0001](../adr/0001-model-frame-is-rub.md), [PLY_MAPPING.md §3](PLY_MAPPING.md)) —
  PLY and SOG each apply it, SPZ applies no conversion, so SPZ's native frame
  *is* the reference frame and the two flipping formats have to agree with it
  and with each other;
- the 15 per-coefficient SH band sign flips, in two independent
  implementations of the same table;
- the three spherical-harmonic memory layouts — PLY stores rest coefficients
  channel-major ([PLY_MAPPING.md §4](PLY_MAPPING.md)), SPZ stores them
  Gaussian-major ([SPZ_MAPPING.md §6](SPZ_MAPPING.md)), SOG stores them as
  coefficient-major palette texels ([SOG_MAPPING.md §6](SOG_MAPPING.md)) —
  reaching one canonical order;
- the quaternion component order, the two SPZ rotation encodings, and SOG's
  smallest-three unpack.

The per-bundle decoder suites check each format against re-derived formulas or
an encode→decode inverse. Those catch a wrong formula; they cannot catch a
formula that is wrong *consistently* on both the encode and decode side. The
cross-format comparison can, because the other format is an independent
witness.

## 2. Tolerance derivation

The fixture generator defines Gaussians in shared-model space and encodes each
one three times. The PLY encoding is exact at float32 — positions, quaternions,
and SH coefficients are stored as-is, and only `log`/`exp` and `logit`/`sigmoid`
round-trips introduce error, at relative 1e-7. **PLY is therefore the reference
side of every comparison and the whole disagreement budget belongs to the
quantizing format.**

### SPZ steps

Each tolerance is half of one SPZ quantization step:

| Attribute | SPZ storage | Step | Tolerance |
| --- | --- | --- | --- |
| position (v2/v3) | 24-bit fixed point, `fractionalBits = 12` | 2⁻¹² | 2⁻¹³ ≈ 1.22e-4 |
| position (v1) | float16 | value-dependent | not paired; see §5 |
| scale | `uint8`, log-encoded, `exp(b/16 - 10)` | 1/16 in log space | relative `exp(1/32) - 1` ≈ 3.18e-2 |
| opacity | `uint8`, `b/255` | 1/255 | 1/510 ≈ 1.96e-3 |
| DC | `uint8`, `(b/255 - 0.5)/0.15` | 1/38.25 | 1/76.5 ≈ 1.31e-2 |
| SH rest | `uint8`, `(b - 128)/128` | 1/128 | 1/256 ≈ 3.91e-3 |
| rotation | see below | see below | 8e-3 |

Scale is the one *relative* tolerance: SPZ quantizes the logarithm, so the
absolute error grows with the value.

Rotation is allowed more than a half step. Both SPZ encodings omit one
component and reconstruct it as `sqrt(1 - Σ)`, whose error is amplified by
`1/(2w)` as the reconstructed component approaches zero. The fixtures keep the
reconstructed component well away from zero, which bounds the amplification;
8e-3 then covers `first-three` (step 1/127.5) with margin, and `smallest-three`
(step `sqrt(1/2)/511`) comfortably.

### SOG steps

SOG's error profile differs in *kind*, not only in size, so it gets its own
bounds ([SOG_MAPPING.md §3-§6](SOG_MAPPING.md)):

| Attribute | SOG storage | Tolerance |
| --- | --- | --- |
| position | 16-bit code across a per-axis **log-domain** range | `(\|p\| + 1) × span / 131070` |
| scale | `exp(codebook[b])`, log-domain codebook | relative 1e-6 |
| DC | `codebook[b]`, raw band-0 coefficient | 1e-6 |
| SH rest | `shCodebook[b]` through the palette | 1e-6 |
| opacity | `uint8`, `b/255` | 1/510 ≈ 1.96e-3 |
| rotation | smallest-three, three `uint8` scaled by `1/sqrt(2)` | 8e-3 |

Two consequences are worth stating explicitly:

- **Positions are bounded relatively, not absolutely.** The encoder quantizes
  `sign(v)·ln(|v|+1)`, so half a code step is `span/131070` *in the log domain*
  and the inverse transform amplifies it by `d/dn(exp(n) − 1) = |p| + 1`. A
  fixture holding a position near 1000 therefore admits ~4e-2 there and ~4e-5
  near the origin — from one derived rule, not two tuned numbers. The generator
  prints the log-domain span of each fixture so the constants in the test can be
  re-derived after any change to the source clouds.
- **Codebooks are exact, so the SH comparison is sharp.** The fixture generator
  fills each 256-entry codebook with the values the cloud actually needs (real
  exports run k-means there), so scales, DC, and every rest coefficient
  round-trip to a few ulps rather than to a quantization step. That is what makes
  a single wrong entry in the 15-sign band table impossible to hide: the
  tolerance is four orders of magnitude below the smallest coefficient in the
  fixtures.

## 3. Two tolerance profiles

Holding an on-grid fixture to the envelope above would let a real structural
error hide inside a tolerance three orders of magnitude looser than the actual
disagreement. So the fixtures come in two kinds:

- **On-grid (`kExact`, 1e-5).** Every attribute except rotation sits exactly on
  an SPZ quantization point, so quantization contributes nothing and only
  float32 rounding remains. This is the sharp structural check.
- **Off-grid (`kEnvelope`).** Arbitrary values chosen *between* quantization
  points, asserting the §2 envelope holds for input that was not selected to
  round-trip.

Rotation uses the envelope value in both profiles: `first-three` stores `w`
implicitly, so no quaternion round-trips exactly — not even the identity.

The SOG suite has the same two profiles (`kSogExact`, `kSogOffGrid`) and they
differ only in the position bound, because SOG's codebooks make every other
attribute exact in both. The two SOG profiles are therefore the same rule
evaluated at two different log-domain spans: 1.096 for the on-grid cloud, 5.488
for the off-grid one, whose largest position is 1000.5.

Values sitting exactly on a half-step boundary are avoided deliberately. At the
boundary the encoder's rounding rule decides the result, so the measured error
would land exactly on the tolerance and the assertion would be a coin flip.

## 4. The SH quantization range is asymmetric

SPZ dequantizes rest coefficients as `(b - 128)/128` with `b` in `0..255`, so
the representable range is **`[-1.0, +0.9921875]`** — not symmetric. Byte 0 is
the one grid point whose negation is *not* on the grid.

Since [ADR 0001](../adr/0001-model-frame-is-rub.md) the band sign flips are
applied by the PLY decoder in float32 space and no longer interact with the
SPZ grid at all. The asymmetry remains a property of the SPZ encoding: a
model coefficient of exactly `+1.0` is unrepresentable and clamps to
`+0.9921875`, an error of one full step (1/128) attributable to the encoder
that wrote the file. The on-grid fixtures draw their SH bytes from `1..255`,
which keeps every fixture value exactly representable in both sign
conventions regardless of where the flip sits.

## 5. What is deliberately not compared

- **v1 float16 positions.** The v1 position path has a value-dependent step and
  is pinned by the SPZ decoder suite against known values instead. Pairing it
  would mean either a tolerance loose enough to be meaningless or fixtures
  restricted to exactly representable float16 values, which tests less than the
  existing v1 fixture already does.
- **The real-asset corpus.** `yashica-t4` and `leica-sofort` are independent
  captures, not two encodings of one reconstruction; the per-format corpora must
  never be diffed against each other. See [SPZ_FORMAT.md §8](SPZ_FORMAT.md).
- **The authored USD stage.** Every bundle authors through the single
  `libs/gaussian-usd` writer, so hierarchy, schema, metadata policy, stage
  metrics, and default-prim behavior are identical by construction and are
  asserted per-bundle by each smoke test. The only intended difference is the
  `sourceFormat` string.
- **SPZ against SOG directly.** Both are compared against the lossless PLY
  reference instead. A direct comparison would add no coverage (agreement with
  a common exact reference implies agreement with each other, at the sum of the
  two envelopes) and would have to be looser than either existing check.

## 6. Where the tests run

`tests/equivalence/` links more than one bundle's decoder library, which no
single bundle can do. It is configured only by the plain root CMake composition
— `ost plugin build <bundle>` configures one bundle and never reaches it — and
runs as the `gaussian_ply_spz_equivalence` and `gaussian_ply_sog_equivalence`
ctests.

They are **two executables rather than one** for a mechanical reason worth
recording: `gaussianSpzDecoder` and `gaussianSogDecoder` each compile their own
copy of the vendored `miniz.c`, with different definitions — SPZ compiles the
archive APIs out, SOG needs them for the bundled `.sog` ZIP — so linking both
static libraries into one program is a duplicate-symbol error, and neither
bundle may include the other's sources
([API_BOUNDARY.md](../architecture/API_BOUNDARY.md) rule 3). Splitting by
quantizing format costs no coverage, since every comparison is against PLY
anyway.
